痛点

它要解决的六个问题

01

只认字面，不认概念

查「结算周期」找不到写「对账频率」的文档；查人带不出他负责的项目。

02

资产散落，无统一索引

Markdown 只是文件，没有「库—文档—切片」结构，也没有可编程的统一入口。

03

变更一致性

文件被改、被删、被移动后，派生索引与实体必须跟得上，否则检索在说谎。

04

本体建模门槛高

手工建类、属性、domain/range 是专家活，普通团队需要一条低成本路径。

05

LLM 的代价

token 膨胀、慢响应超时、幻觉输出——省成本、抗失败、防幻觉必须工程化。

06

被外部消费

Web、Dify、MCP、自研应用都要用同一份检索逻辑、同一个契约接入。

差异

与传统知识库系统的五个不同

D1

向量索引 + 本体图谱双索引

不只存切片向量，还存 OWL 2 RL 本体与实体关系；检索可沿关系扩展召回。

D2

锚点三元组回源

每一切片与实体锚定（相对路径, 序号, 哈希），命中可逐字回读权威源原文。

D3

两阶段 LLM 建模 + 人工裁决

先归纳本体、确认后抽取实体关系；全部进待处理队列，确认/拒绝/编辑，机器不静默做主。

D4

删除与冲突显式化

删文件、删类、改 range 产生的实体/关系问题全部转待处理，不静默丢弃。

D5

面向智能体的契约

同一检索编排对外提供 HTTP / Dify 契约 / MCP 三套入口，可被外部系统实时挂接。

关联

不同点 ↔ 待解决问题的对应关系

不同点解决哪些问题对应关系
D1 双索引（向量 + 本体图谱）P1 不认概念 / P6 被消费本体承载概念层，关系扩展把「带出关联实体」变成检索能力
D2 锚点回源P2 无结构 / P3 变更一致性锚点把派生物与权威源绑定，改/删可检测、命中可核对
D3 两阶段建模 + 裁决P4 建模门槛 / P5 LLM 代价机器归纳候选、人来确认，幻觉在入口被校验丢弃
D4 删除与冲突显式化P3 变更一致性任何影响实例的变更都落到待处理队列，可追溯可裁决
D5 智能体契约P6 被外部消费一套编排三入口，外部系统零导入实时借力
架构

技术架构：三层 + 双索引

权威源Markdown 目录（只读）
→
切片 & 嵌入标题层级切块 · text-embedding-v4
→
检索索引Qdrant（向量 + 载荷）
→
语义索引Neo4j（本体 + 实体图谱）

服务层

FastAPI + arq 任务队列（Redis）；同步/重建/归纳/抽取均为幂等任务，同库同类单飞。

消费层

Web 界面 · Dify 外部知识库契约 · MCP 工具 · 自研 HTTP 调用，共用同一检索编排。

建模层

qwen3.8-flash 归纳与抽取（关思考、签名裁剪、断点续抽）；OWL 2 RL 校验 + TTL 导入导出。

全部组件单机 Docker 部署，端口仅绑定 127.0.0.1；密钥只经环境变量注入。

建模

两阶段知识建模：先本体，后实体

阶段一 · 本体归纳

从语料归纳候选本体

采样切片 → LLM 归纳类/对象属性/数据属性（中文标签、定义、domain/range 引用）→ 本体提案 → 确认后入注册表并导出 TTL。

阶段二 · 实体与关系抽取

按已确认本体抽取

签名只取标签命中切片的类；实体名必须逐字在正文、IRI 必须在本体签名内 → 提案 → 确认后成为实体与关系，参与检索扩展。

生成期结构校验（属性引用缺失类不进入队列）+ 确认期冲突提示（重复自动关闭、缺失标签列出可选并跳转定位）——机器产出、人工拍板。

本体页：类 / 对象属性 / 数据属性
LLM 辅助建模：归纳本体 → 抽取实体与关系
可靠

一致性与可靠性设计

R1

增量同步

内容哈希门槛；删除文档自动清索引、锚定实体转待处理。

R2

任务幂等 + 单飞

重试不重复建记录/提案；同库同类任务同一时刻只跑一个。

R3

断点续抽

已成功切片永久跳过，重跑只补失败与缺失，不重复计费。

R4

显式失败

部分失败任务标记 partial，失败清单进队列，从不静默丢弃。

R5

整库可重建

删除两个索引卷即可从权威源 + TTL 全量重建；重建前预估与二次确认。

R6

边界

端口仅本机、单一 Bearer 令牌、密钥不进日志与导出。

成本

LLM 成本与质量工程

曾经

思考模式 + 全量签名

单次调用 2~2.5 万 token，超时失败的服务端计费难控，两天烧掉约 200 元。

现在

flash + 关思考 + 签名裁剪

单次约 1.1K token、十余秒；千片级抽取总费用数元级，失败切片只补差额。

教训：模型的「默认聪明」是计费的——机械 JSON 任务不需要思考链；签名只送与切片相关的要素；超时失败也要当作成本来管。

落地

企业实施步骤（大体）

第 1 步

定资产与边界

盘点 Markdown 知识资产，划定语料库目录（一个库 = 一个子目录）。

第 2 步

小范围部署

先在单机/开发环境用 Docker Compose 起栈（Qdrant/Neo4j/Redis/API/Worker/Web），配置密钥与端口，验证检索与建模闭环。

第 3 步

建库同步

新建语料库 → 全量同步入索引；此后增量同步/定时轮询自动跟进变更。

第 4 步

建模与裁决

LLM 归纳本体 → 确认 → 抽取实体与关系 → 确认；重复迭代直至覆盖满意。

第 5 步

接入消费方

Web 检索验证 → Dify 契约 / MCP / 外部智能体挂接（不导入、实时访问、显式降级）。

第 6 步

逐步加大部署

以语料库为单位扩容：逐域同步与建模，观察成本与质量后扩大并发与范围，再把 API 开放给更多消费方。

库管理：建库、同步、归档、拖拽排序
检索测试：命中片段与锚点回源
